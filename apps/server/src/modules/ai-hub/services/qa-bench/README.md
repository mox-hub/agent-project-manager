# CAP-C-07 问答质量基线测评集（qa-bench）

> AISlot 局部侵入问答（「哪里不懂点哪里」，Ctrl/Cmd+左键实体卡）的回答质量基线。
> 需求重审裁决（2026-09-17，批二 P1）：**「只复述字段者砍，能行动者留」**。
> 本期动作 = 测评基建 + 基线；砍/改功能由人工终审报告驱动，**不在本期动作内**。

## 一、这是什么

| 层 | 载体 | 谁跑 | 依赖 |
| --- | --- | --- | --- |
| **确定性层** | `qa-bench.spec.ts`（CI 可跑） | CI / `pnpm --filter server test` | 零真实 LLM——LLM 经 `AdapterRegistryService` 注入 mock adapter，prisma 用夹具 stub |
| **人工终审层** | 本 README 的问题集 + rubric + 采集指引 | 人（按 §五采集、按 §四评分、按 §六出报告） | 开发环境实机调用 |

确定性层回答「链路与规则是否自洽」：夹具事实确实注入指令（grounding 上游确定成立）、评分器语义正确、实体不存在守卫 400。**它不能证明真实 LLM 回答合格**——那由人工终审层承载。

## 三、问题集概览（8 类 × 3 问法 = 24 条）

覆盖 AISlot 八类实体（`data-ai-entity` kind，与 `assistant-silent.service.ts` 的 `loadCardEntityFacts` 支持面一致）：

| 实体 | 字段查询类 | 行动建议类 | 边界探测类（夹具缺口） |
| --- | --- | --- | --- |
| task（任务卡） | 这张卡现在处于什么状态？ | 这张卡接下来该做什么？ | 什么时候到期？（dueDate=null） |
| decision（决策卡） | 这个提案批了没有？ | 下一步该怎么处理？ | 谁驳回的？理由？（resolution=null） |
| member（成员卡） | 信任分是多少？ | 现在能接执行任务吗？ | 负责哪些项目？（事实无项目归属） |
| acceptance（验收卡） | 过审了吗？卡在哪？ | 要通过该先做什么？ | 审计什么时候跑的？（auditDate=null） |
| project（项目卡） | 现在健康吗？ | 接下来最该盯什么？ | 花了多少钱？（事实无成本口径） |
| team（团队卡） | 有什么协作规则？ | 新成员该先做什么？ | 有哪些成员？（事实无名册） |
| contract-binding（契约绑定卡） | 有冲突吗？ | 冲突该怎么处理？ | 谁创建的？（事实无创建人） |
| document（文档卡） | 发布了吗？ | 接下来该做什么？ | 作者是谁？（事实无作者字段） |

## 四、三要素 rubric（合格线 = 三中二）

对每条「问题 × 采集答案」打 0/1 分：

| 要素 | 判法 | 1 分 | 0 分 |
| --- | --- | --- | --- |
| ① 能行动 | 启发式：答案（summary+details+nextStep）命中行动信号词表（`ACTION_SIGNALS`：建议/下一步/先/发起/提交/确认…） | 给出了下一步或可执行建议 | 只描述状态，没有行动形状 |
| ② 有依据 | 规则化：答案引用夹具事实的期望子串（`mustMentionAny`，组内任一命中；仅字段查询题配置） | 期望字段值在答案中可溯源 | 复述了字段却没引用真实值 / 泛泛而谈 |
| ③ 守边界 | 边界题：命中守边界信号词表（`BOUNDARY_SIGNALS`：没有数据/暂无/未提供/这一点我没有数据…）；其余题：日期编造检测（答案中的具体日期必须能在实体事实中找到） | 承认数据不足 / 引用均可溯源 | 编造（边界题不承认缺口；其余题出现事实外的日期） |

**合格线**：参与判定维度中得 1 分的个数 ≥ 2。因行动题/边界题不配「有依据」期望，它们自然收严为「双维全过」——这正是「只复述字段者砍，能行动者留」的规则化落点。

**启发式局限（人工终审必须复核）**：

- 行动词表判「有建议的形状」，判不了建议是否正确、是否可落地（「检查一下」也算命中）；
- 有依据判「引用了期望值」，判不了引用是否用对语境（张冠李戴不扣分）；
- 守边界的日期检测只覆盖「编造具体日期」；人名/数字/事件的编造、以及「先承认没数据再顺手编一个」的混合逃逸，靠人工终审把关。

## 五、答案样本采集指引（人工终审层）

### 前置

1. 启动开发环境：仓库根 `pnpm dev`（server + frontend）。
2. 准备一个工作区与项目，**造出与 §三 矩阵对应的真实数据**：每类实体各建 1 条（任务、决策提案、成员、验收、项目、团队、契约绑定、文档），并给边界题留出真实缺口（如任务不填截止日期）。
3. 登录前端拿到 JWT（或直接用前端 UI 采集，见方式 B）。

### 方式 A：端点直采（可脚本化批量）

静默 AI 统一入口：`POST /_api/ai/assistant/silent`，AISlot 走的场景是 `card-explain`：

```bash
curl -X POST http://localhost:3000/_api/ai/assistant/silent \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <JWT>" \
  -H "x-workspace-id: <工作区ID>" \
  -d '{
    "scenario": "card-explain",
    "context": {
      "entity": { "kind": "task", "id": "<真实实体id>" },
      "question": "这张卡现在处于什么状态？"
    }
  }'
```

- 响应 `{ scenario, data }`，`data` 即结构化答案 `{ title, summary, details, nextStep }`——原样贴进评分表。
- `kind` 取值：`task / decision / member / acceptance / project / team / contract-binding / document`。
- 每条问题采集 1 次；建议对不达标条目间隔重采 1 次再定论（LLM 有波动）。

### 方式 B：UI 实采（最贴近真实手感）

1. 前端进入任意展示实体卡片的页面。
2. **长按 Ctrl/Cmd 约 0.5 秒**（全部可解释卡高亮），松开后 **Ctrl/Cmd+左键点卡片**——AISlot 解释卡在原位展开。
3. 问题原文即 §三 矩阵中的问法（AISlot 默认无显式问题；带问题采集走方式 A 的 `context.question`，两者都建议采——差异本身是终审素材）。
4. 截图 + 复制解释卡全文进评分表。

### 采集注意

- 同一实体不要连续采集间隔过短（有静默调用成本，AIUsageLog 记账）；
- 边界探测题若答案承认缺口，**不要顺手把数据补上再采**——先记录，再补数据、再采一次对照；
- 采集时记录 model/provider（回执 `usage.model`），终审报告需注明基线是哪个模型跑出来的。

## 七、确定性层设计取舍

1. **为什么能走真链路而不依赖真 LLM**：`AssistantSilentService` 的三个依赖（Prisma / AdapterRegistry / UsagePricing）全部构造函数注入；现有测试已经用 mock adapter 走 `run()` 全链路。本测评集沿用同一手法：夹具 stub 提供事实 → `prepareContext` 真的查「库」（stub）→ `buildInstructions` 真的组装指令 → 假 adapter 返回预设样本 → `extractJsonObject` 真的解析 → 评分器真的打分。**确定性层守的是「管道保证有依据的上游条件成立 + 规则可执行」，不冒充质量结论。**
2. **为什么边界题不做日期检测、行动题不配有依据期望**：边界题的期望就是「承认缺口」，信号词直接对准；行动题配了依据期望会把合格线放松回「三中二三稀释」，去掉后「双维全过」才是裁决要的收严。
3. **词表启发式的误报/漏报**在 §四「局限」中明示，误判纠正记在评分表「终审备注」列，作为后续把规则升级为模型判分的输入。
4. **零行为变更**：本期未改任何既有功能代码（`assistant-silent.service.ts` 等零 diff），全部产物为 ai-hub 域内新增测试基建文件；不动 openapi.json。

## 八、改进一轮机制（不达标先改再砍）

1. 终审发现不达标条目 → 在报告 §三 写改进建议（通常是改 `card-explain` 场景指令口径，或把问法/夹具缺口调整得更合理）；
2. 改动落码后重跑确定性层 spec（`pnpm --filter server test -- qa-bench`）+ 重采该条目样本；
3. 复测仍不达标 → 进报告 §四 砍/改建议清单，由人工裁决是否砍功能或撤问题。
