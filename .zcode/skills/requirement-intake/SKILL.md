# 需求入口闸门（requirement-intake）

本仓库存在一份需求真相账本：`docs/01-需求/能力清单-v1.md`（配套 `测试映射矩阵-v1.md`、`需求入口流程-v1.md`）。**任何新功能想法、功能变更、功能废弃意图，在动手写代码或写设计纪要之前，必须先走完以下五步。**

## 触发信号

用户表达中出现（不限于）：

- "要不要加…"、"如果能有…就好了"、"我想让…"（新功能）
- "把 X 改成…"、"X 的语义应该是…"（功能变更）
- "X 不要了"、"砍掉 X"（废弃）

## 五步流程（顺序执行，不得跳步）

1. **一行声明**：把想法压成「用户价值 + 影响域」一句话，向用户复述确认。
2. **冲突检测**：Read `docs/01-需求/能力清单-v1.md`，逐线检查——是否已有卡片覆盖？是否修改既有卡（列出卡 ID）？是否与 §五治理骨架分工（acceptance=验收证据层 / contract=文件绑定层）或 §二主轴（AI 同事是手段、治理是目的）冲突？向用户报告重叠与冲突。
3. **裁决归档**：给出建议后由用户三选一——立即开工 / 进候补区 / 放弃（放弃必须留一句理由）。
4. **更新清单**（Edit 能力清单）：
   - 候补 → §六候补区加一行（日期/声明/影响域/状态 pending）。
   - 新卡 → 按归属线分配 ID（A 底盘 / B 治理 / C 同事 / K 契约知识 / X 跨线桥 / P 规划），状态 `planned`，含用户价值、承载模块、溯源、测试映射字段。
   - 变更写入 §七变更记录表。
5. **开工登记**（仅"立即开工"）：卡状态置 `doing`；在测试映射矩阵缺口表加对应 GAP 行或登记用例义务；**若属 C 同事线，必须先补供血判据**（`†供血 CAP-B-xx`——答不出供血哪条治理能力的，强制回候补区）；**新卡必答六问**（见下节），老卡复审时补答。

## 六问评审标准（2026-09-17 需求重审裁决 1 增，新卡必答）

开工登记时向用户逐问确认，答案写入卡片：

1. **用户任务**：用户最终要完成什么，而不是打开什么页面？
2. **AI 职责**：AI 在哪个环节提供不可替代的帮助？不需要 AI 也可明确说明。
3. **可信依据**：建议与结论依赖什么事实、规则、版本与证据？
4. **人类控制**：哪些事需要人决定？怎样保证人真正理解而非机械确认？（「人确认」不得成为责任转移）
5. **失败与降级**：AI 错了、不可用、信息不足时，用户怎么继续？
6. **跨模块闭环**：输入从哪里来，输出交给谁，变更后如何重新对齐？

红线：AI 不得自己生成标准、自己宣称符合、再把自己的结论当作独立证据（详见 `docs/01-需求/需求重审-总纲-v1.md` §2.2/§三）。

## 硬规则

- **未进清单的功能不得开工**。设计纪要照常可写（架构真相源），但纪要对应的能力卡登记是开工前置条件。
- 废弃/降级不删卡：置 `gap` + 理由。
- 新功能卡的测试义务：正常流 + ≥1 异常流 + 涉及的联动场景；修 bug 必配回归用例（见测试映射矩阵 §六）。另须覆盖**两类质量**：工程规则是否守住（不越权/不误用旧证据/不绕门禁/状态口径与数据模型一致）+ AI 是否真的帮上忙（识别信息不足/说明依据/接受纠正，而非只测「生成了一段文本」）。
- 状态词表仅 `planned / doing / done / gap`。

## 完成后

向用户报告：卡片 ID、清单 diff 摘要、测试义务。若为候补区归档，告知裁决日期以便未来复盘。
