# H 类修改方案：画廊遍历渲染与 100% 覆盖率门禁

> **六项决策（含两处排版）已于 2026-09-29 全部落定（§2.3 / §四），方案转待开工。** 一行声明：让「组件进了 registry 却在画廊找不到」从静默缺口变成机器强制的硬门禁——每个登记组件要么有 demo、要么带理由显式豁免，覆盖率恒 100%。

## 〇、宣称与现实的差距

`registry.ts` 文件头（②同源链）与 `gen-components-md.mjs` 文件头（②环）**都宣称**「registry.ts ──渲染──► design-system 页（按 section 遍历 registry，覆盖率恒 100%）」。**实测（2026-09-29，分支 refactor/design-semantic-tokens）该宣称未兑现**：

- `design-system-page.tsx`（6416 行）仍是手写形态：手写 import + 手写 SECTIONS（90 条）+ 手写正文 JSX；页面不 import `COMPONENT_REGISTRY`。
- `check-component-registry.mjs` §4.2 ④ 按页面 import 口径实测：**画廊覆盖 76/100 = 76.0%**（仅 ui 层机查，报告项不做门禁）。
- 三层登记覆盖率则已是 100%：ui 100 条、raw 2 条、semantic 6 条与三目录双向对账零缺失、零死条目（registry 共 342 条全绿）。

**结论**：缺的不是登记，是「登记 → 画廊收录」这一跳的闭环与强制。

## 一、实测现状：24 个未收录件四分类

| 类 | 件数 | 清单 | 处置 |
|----|------|------|------|
| ① canonical 真·画廊缺口 | 12 | chart、data-table、table、form、field、item、sidebar-panel、right-sidebar、tab-bar、quick-cards-toggle、ai-agent-badge、ai-context-summary | **补 demo**（21–456 行中小件，成本可控） |
| ② review/standby 待裁决休眠件 | 6 | anchored-menu、direction、navigation-menu、sidebar、view-display-popover（review×5，proposal 均 delete）+ app-dock（standby，proposal delete） | **豁免**（随裁决清退，不单独补 demo） |
| ③ 运行时挂载/兜底件 | 4 | error-boundary、global-loading-state、mock-badge、page-error-fallback | **豁免**（main.tsx/错误边界挂载，非可 demo 形态） |
| ④ .ts 工具件 | 2 | menu-surface（菜单定位）、tone（色彩工具） | **豁免**（非可视组件，无可视 demo） |

另有 raw 层 2 件（raw-button/raw-input）按裁决 G6 登记 internal 态、不出画廊——**已属制度性豁免**，不计入未收录账。

## 二、方案设计

### 2.1 registry 显式豁免槽位（fail-closed）

`ComponentEntry` 增加可选槽位 `galleryExempt?: string`（豁免理由，一句话）：

- **选显式槽位而非规则推导**：规则推导（如「.ts 文件自动豁免」）会让豁免变隐性口径、复审时无从问责；显式槽位与 `expiresAt` / `review` 块同风格，机器可数、人工可裁决。
- **条目保持严格单行字面量**（registry 头注既定纪律）：`galleryExempt` 书写位置紧跟 `status` 之后。两个纯 node 解析脚本（`gen-components-md.mjs`、`check-component-registry.mjs`）的 `ENTRY_RE` **同批同步**非捕获组——脚本已有「解析条数 ≠ `status:` 出现次数即报错」兜底，格式漂移会当场红。
- `gen-components-md.mjs` 在 COMPONENTS.md 渲染豁免列，保持再生产物与 registry 同源。

### 2.2 覆盖率门禁转 error（口径扩至 ui + semantic）

`check-component-registry.mjs` §4.2 ④ 从报告项升级为硬门禁：

- **分母** = registry 中 file 为 `ui/` 或 `semantic/` 前缀、status ≠ internal、且无 `galleryExempt` 的条目（raw/internal 按 G6 豁免既有口径不变；**semantic 首次纳入机查**——现脚本只查 ui/，semantic 6 件已全覆盖，扩口径零存量成本）。
- **分子** = 画廊页 import 命中（现口径沿用）。
- **任何缺失条目 → 退出码 1**。无存量基线缓冲（豁免槽位本身就是缓冲，不必再设 LU_BASELINE 式豁免账）。

### 2.3 画廊「Registry 对账区」——遍历渲染的最小兑现

`design-system-page.tsx` 新增一个 section（SECTIONS +1 条，group 归 Governance，物理序挂正文末尾、零正文搬移）：

> **排版裁决（2026-09-29，用户拍板）**：① 位置 = **正文末尾·Governance 组**（零正文搬移，与「组件裁决面」等治理分区聚拢，侧导航可达）；② 形态 = **紧凑表格**（组件名/状态/文件/豁免理由四列行式布局，与画廊现有治理区表格语言一致）。本方案内两处排版决策已全部裁决完毕。

- **首次 import `COMPONENT_REGISTRY`**，按 registry 遍历生成两张清单卡：
  - **未收录占位卡**（若无豁免且未 import——门禁转 error 后常态应为空，防回归可见化）；
  - **豁免清单卡**（galleryExempt 条目：组件名 / 状态 / 文件 / 豁免理由）。
- 效果：缺口与豁免从「跑脚本才知道」变成「打开画廊就看到」，实机验收有抓手。
- 兑现两处头注宣称的**第一层**（清单级遍历）；正文 section 骨架的完全 registry 驱动见 2.4。

### 2.4 远期：正文骨架 registry 驱动（与 G2 遗留账合并，本方案不实施）

正文 ~4000 行物理搬移本就是 G 类批 G2 第三轮登记的遗留账（含滚动判定序重对齐）；搬移时顺势将各组「组内条目卡」改为 registry 遍历生成，才到达头注宣称的完全形态。与「统计卡六套归一」「ChartContainer vs 裸 ResponsiveContainer 二选一」两遗留账同工地，须前后错开、不可同批。**本方案只立项不实施**，防止 6400 行大轮子（设计治理域禁全库大轮的既定纪律）。

- **改动范围**：全部限定在 design-system 模块 + 两个治理脚本 + registry + 再生产物，**业务面零改动**。
