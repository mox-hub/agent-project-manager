# G5 执行隔离与成果合入设计 v1

> 2026-10-01 设计定版（v0.7.11 交付物），v0.7.12 按本稿实现。上游依据：需求重审总纲 §4.3 G5（已核实缺口）、2026-09-17 裁决 C「执行级子目录隔离无法脱离合入机制单独落地，隔离+成果合入另立设计切片（候选：git worktree + 合入走决策卡）」。
> **本稿两项用户裁决（2026-10-01 AskUserQuestion）**：①合入门形态=**决策卡人工确认**（执行成功≠自动进主工作区）；②隔离不可用降级=**回落共享根 + 显眼标记**（不阻塞派发）。

## 一、背景与缺口

需求重审已核实的 G5 缺口：**并行执行无隔离、无合并**——派发 cwd 恒为项目级共享工作区根（`dispatch.service.ts` `getWorkspaceRoot` 三级 fallback），两个执行同时在共享根目录跑即是脏写风险的直接来源；执行成果与用户本地未提交变更之间没有任何隔离与合入边界。

2026-09-17 批一切片 1+2 已落**单活跃互斥**（`createExecutionRun` 应用层检查 `ACTIVE_EXECUTION_STATUSES`），但互斥解决的是任务语义（同 issue 重复执行无意义），不解决**跨 issue 并行**时的目录脏写，也不解决「AI 改动如何可信地进入用户主工作区」。

**非目标（PRD §15 继续有效）**：不做多 agent 协同调度编排。本设计只补最小执行隔离与成果合入，不含任务排队、资源配额、多机调度。

## 三、总体方案

```
派发（dispatch runDispatch）
  ├─ getWorkspaceRoot 三级 fallback（不变）
  ├─ [新增] 隔离准备：root 是 git 仓库？
  │     ├─ 是 → git worktree add -b apm/exec/<shortId> <root>/.apm/worktrees/<shortId> HEAD
  │     │        成功 → workspaceRoot := worktree 路径；metadata.isolation={mode:'worktree',...}
  │     │        失败 → 降级（§5.3）
  │     └─ 否 → 降级（§5.3）
  └─ 派发载荷（cliInput / createDispatch）照旧组装——协议零变更

执行完成（completeExecution / runtime.execution.result）
  └─ [新增] 成果收集：worktree 内 diff/commits → 空则直接清理；
        有变更 → 补快照 commit → 创建 integration 决策卡（含人话摘要）

决策（DecisionProposal kind='integration'）
  ├─ accept → applier：fingerprint 校验 → 主工作区 clean 校验 → merge-tree 冲突预检
  │           → git merge --no-ff → 清理 worktree+分支 → 记账 mergeCommit
  ├─ reject → 清理 worktree+分支 → 记账
  └─ 冲突/脏工作区 → 拒绝本次 accept（卡保持 pending，附可读原因）
```

## 四、裁决与依据

| # | 裁决点 | 结论（2026-10-01 用户裁决） | 依据 |
|---|--------|--------------------------|------|
| 1 | 合入门形态 | **决策卡人工确认** | 「AI 建议→人确认」主轴；工程化可信度定位；内测期信任压力最小 |
| 2 | 隔离降级 | **回落共享根 + 显眼标记** | 非 git 项目本无法 worktree，fail-closed 等于砍掉该类用户；诚实降级优于静默或阻塞 |
| 3 | worktree 落点（工程自决） | `<项目根>/.apm/worktrees/<shortId>`，幂等补 `.gitignore` | 同盘符防跨盘失败；用户可见可清理；删项目即全清。`.gitignore` 追加一行属最小侵入且幂等 |
| 4 | 冲突探测（工程自决） | `git merge-tree --write-tree` 无副作用预检 | 真 merge 失败会把主工作区留在冲突态，污染用户现场；预检失败不落任何副作用 |
| 5 | worktree 保留期（工程自决） | 失败执行保留供诊断，reconcile 巡检 7 天 TTL 清理；成功但未决卡的超时清理随 reject/巡检 | 失败现场是诊断资产；TTL 防垃圾积累 |

## 五、详细设计

### 5.1 新服务 `ExecutionWorktreeService`（modules/cli-dispatch 或 modules/git 下）

受控白名单式封装（**独立 execFile 通道，不走 GitCommandService 的用户输入黑名单**——黑名单管的是 API 层任意命令，本服务命令集全部程序内构造）：

- `prepareWorktree(projectRoot, executionId)` → `{worktreePath, branch, baseRef}`：`rev-parse --is-inside-work-tree` → `worktree add -b apm/exec/<shortId> <path> HEAD`（shortId=executionId 后 8 位）；幂等补 `.gitignore`（`.apm/` 条目不存在才追加）。
- `collectChanges(worktreePath, baseRef)` → `{hasChanges, commitCount, diffStat, files[], headRef}`：`status --porcelain`（有未提交变更则 `add -A` + 受控 commit，message `chore(apm): execution <shortId> snapshot`，author 取执行主体）+ `diff --stat <baseRef>..HEAD` + `log --oneline <baseRef>..HEAD`。
- `detectConflicts(projectRoot, branch)` → `{clean, files[]}`：`merge-tree --write-tree HEAD <branch>`，退出码/输出解析冲突文件清单。
- `integrate(projectRoot, branch, message)` → `{mergeCommit}`：主工作区 `merge --no-ff <branch> -m <message>`。
- `cleanup(projectRoot, worktreePath, branch, {force})`：`worktree remove [--force]` + `branch -D apm/exec/...`（**仅删 `apm/exec/` 前缀**，前缀校验硬编码）。
- `inspect(projectRoot)` → 巡检孤儿与悬挂元数据：`worktree list --porcelain` + `worktree prune`。

### 5.2 派发链注入（两条路径同时生效）

`runDispatch` 在 `getWorkspaceRoot` 之后追加「隔离准备」步骤（try/catch 全包）：

- 成功 → `workspaceRoot` 变量替换为 worktree 路径（进程内 `cliInput` 与 daemon `createDispatch` 载荷自动同源生效）；`Execution.metadata.isolation = { mode:'worktree', worktreePath, branch, baseRef }`。
- 失败/不适用 → `metadata.isolation = { mode:'shared-root', reason }`，reason ∈ `not-git-repo | worktree-add-failed | disabled`，worktree-add-failed 附原始错误摘要。
- 配置逃生门：AppConfig `scope='execution', key='isolation.mode'`（`worktree`（默认）| `shared-root`），无 UI，文档级配置。
- `CliSession`/`CliExecutionBinding` 的 workspaceRoot 落 worktree 路径——执行面板回读即所见即所得。

### 5.3 降级口径（裁决 2）

降级**不阻塞派发**，但三处显眼：①执行详情隔离徽标（琥珀色「未隔离·共享目录」+ reason tooltip）；②执行列表同徽标；③若产 integration 决策卡（共享根下 agent 直接改主工作区，无 worktree 可合入），卡内顶部警示「本次执行未隔离，改动已直接发生在主工作区」。共享根路径**不发合入卡**（无 branch 可 merge，卡只会造成困惑）。

### 5.4 成果收集与决策卡创建

挂 `completeExecution` 成功路径（进程内与 daemon 两路已同源汇于此；`persistCompletionEvidence` 附近）：

1. `metadata.isolation.mode !== 'worktree'` → 跳过。
2. `collectChanges`：空变更 → 清理 worktree+分支，`metadata.integration={status:'no-changes'}`，不发卡。
3. 有变更 → 创建决策卡：kind=`integration`（枚举追加），`title` 人话（「AI 执行完成：N 个文件 +X −Y，建议合入」），`payload={executionId, issueId, worktreePath, branch, baseRef, headRef, diffStat, files(top 20), commitCount, mainDirty}`，`approvedFingerprint = headRef`（分支冻结后不再变，指纹防的是卡创建后分支被外部动过）。`ensureNoPending` 去重复用（同 executionId 维度）。
4. 失败/取消执行：不发卡；失败保留 worktree 供诊断（`metadata.isolation` 已含路径，详情页可见）；取消/superseded 立即清理。

### 5.5 applier（accept 副作用，事务外 git + 事务内记账）

`proposal.service` applier 新增 `integration` 分支：

1. worktree/分支存在性校验（被外部手动删 → 可读错误「执行现场已清理，无法合入」）。
2. `approvedFingerprint === 当前分支 HEAD`，不符 → 错误「执行现场在批准后发生变化，请重新查看」。
3. 主工作区 `status --porcelain` 非空 → 错误「主工作区有未提交变更，请先处理后再合入」（列出前 5 个文件）。payload.mainDirty 已在卡创建时预检过一次，此处是决策时刻复核。
4. `detectConflicts` 预检冲突 → 错误「与主工作区当前进度存在冲突」，附冲突文件清单；卡保持 pending，用户可改选拒绝。
5. `integrate` 真合入 → 清理 worktree+分支 → `Execution.metadata.integration={status:'merged', mergedAt, mergeCommit}`，resolution 记 mergeCommit。
6. git 步骤在事务外逐步执行（git 无事务），记账（metadata/resolution）在事务内；中途失败按已发生步骤幂等收拾（如已 merge 但记账失败 → 复查 mergeCommit 补记账）。

`reject` 分支：`cleanup(force:true)`（未合入分支须 `-D`）+ `Execution.metadata.integration={status:'rejected'}`。

### 5.6 单活跃互斥加固

- **必做**：收口 `issue.service.ts:1939-1948` 直创路径——加同款 `ACTIVE_EXECUTION_STATUSES` 检查（复用 execution.service 导出的常量与判定函数）。
- **选做（工时允许）**：SQLite partial unique index 迁移（raw SQL）：`CREATE UNIQUE INDEX execution_issue_active_uq ON Execution(issueId) WHERE issueId IS NOT NULL AND status IN ('planned','in_progress','pending_approval','blocked')`。表名/状态字符串以实库为准，实现时核实 `@@map`。

| 位置 | 内容 |

## 六、测试义务（GAP-T-53 登记）

- **单元**：prepareWorktree（正常/非 git/分支已存在）、collectChanges（空/仅未提交/仅 commits/混合）、detectConflicts（无冲突/冲突文件解析）、integrate（ff 场景 --no-ff 产 merge commit）、cleanup 前缀校验（非 `apm/exec/` 前缀拒删）、applier 六步各自失败分支、指纹不匹配、脏工作区复核。
- **集成**（临时 git 仓库 fixture，**不 spawn 真 CLI**——真实 LLM 风险红线）：派发注入后 cliInput/createDispatch 载荷断言；completeExecution → 决策卡创建 payload 断言；reject 清理链。
- **e2e**：既有派发 e2e 增断言 `metadata.isolation` 字段形状；不新增真实执行链 e2e。
- **测试映射矩阵**：GAP-T-53（G5 隔离与合入，P0）随实现登记。

## 七、风险与开放问题

| 风险 | 处置 |
|------|------|
| 用户手动删 `.apm/worktrees` 或手工 git 操作致悬挂 | applier 存在性校验 + reconcile `worktree prune` 巡检；错误信息可读 |
| merge --no-ff 后主工作区构建态被破坏 | 与普通人工 merge 同险，git revert 可逆；决策卡摘要给足上下文 |
| daemon 在异机？ | APM runtime 为本机守护进程（同文件系统），不成立；若未来远程 runtime 落地，worktree 需随协议上移——ADR 留记 |
| 长 merge 冲突清单卡详情爆量 | payload files top 20 + 冲突清单 top 20，溢出计数 |
| `git merge-tree` 需 git ≥ 2.38 | prepareWorktree 前 `git --version` 探测（GitToolService 已有能力），低于 2.38 视同降级 reason=`git-too-old` |

**开放问题（实现期裁决，不阻塞）**：snapshot commit 的 author 邮箱口径（执行主体 Member 无邮箱时用 `execution@apm.local` 占位）；`.gitignore` 用户仓库被只读锁定时的静默跳过（worktree 目录变 untracked 可接受）。

## 八、v0.7.12 实施边界

**后端**：ExecutionWorktreeService + dispatch 注入 + completeExecution 成果收集 + proposal kind=`integration` 枚举与 applier + 互斥绕过收口 + reconcile 巡检 + 开关配置读取。**前端**：执行详情隔离徽标与信息行 + 收件箱 integration 卡 + i18n。**契约**：无新端点（决策卡 resolve 复用既有）；若卡 payload 对外暴露则 openapi 模型同步。**不含**：隔离配置 UI、worktree 手动管理 UI、共享根执行的事后 diff 展示（留后续切片）。
