# 移动端发布与分发方案

**一期范围（`CAP-M-10` 边界）**：**只做内测分发**。不追求当期 App Store / Google Play 正式上架运营（上架涉及审核、隐私政策、商店素材、评分治理，属独立工作包）。**内测通道足够支撑 M1–M3 的全部验证需求**。

---

## 一、三件套（EAS）

| 工具 | 用途 | 触发时机 |
|---|---|---|
| **EAS Build** | 云端构建原生二进制（免本地 Xcode/Gradle 环境） | 发版 / 新原生依赖 / SDK 升级 |
| **EAS Submit** | 提交构建产物到 TestFlight / Play 内部测试轨道 | 内测版本 |
| **EAS Update** | **OTA 热更** JS bundle（不改原生代码时） | 日常修复与迭代 |

**profiles（`eas.json`）**：

| profile | 用途 | 分发 | 环境 |
|---|---|---|---|
| `development` | 本地开发（dev client） | 内部 | dev server |
| `preview` | **内测**（主通道） | TestFlight / Play 内部测试 / APK 直发 | 指向预发或生产 server |
| `production` | 正式上架（**一期不做**） | 商店 | 生产 server |

---

## 二、iOS（内测）

1. **账号**：Apple Developer Program（年费）；App ID 与 Bundle ID 在 `app.json` 固化（**建号后不得改**，改了等于换 App）。
2. **证书与描述文件**：**交给 EAS 托管**（`eas credentials`）——本地不存 `.p12` / `.mobileprovision`（避免证书私有状态散落在个人机器上）。若走自管，须入公司密钥库并登记轮换周期。
3. **内测通道**：**TestFlight**（内部测试员 ≤ 100 无需审核；外部测试需 Apple 简审）。
4. **推送**：APNs Key（`.p8`，**可用同一 Key 跨环境**）上传至 EAS + server；Key ID / Team ID 入 server 配置（**不入仓库**，走环境变量/密钥管理）。
5. **能力开关**：Push Notifications、Associated Domains（Universal Links）。

## 三、Android（内测）

1. **签名**：`keystore`（`.jks`）——**这是 Android 唯一不可再生的凭据**（丢失则无法对已装用户更新，只能换包名重发）。**必须**入公司密钥库备份（至少两份异地），`eas credentials` 托管为备。
2. **分发通道**：Google Play **内部测试**轨道（快速、≤100 测试员）；或 **APK 直发**（内测期最快，但无自动更新——需配合 EAS Update 或手动换包）。
3. **推送**：FCM（`google-services.json`）+ FCM v1 服务账号 Key；同样不入仓库。
4. **能力开关**：App Links（`assetlinks.json` 由 server 域名提供）。

---

## 四、OTA 与 runtimeVersion 策略（关键约束）

**核心规则**：**OTA 只能推 JS/资源，不能改原生**。`runtimeVersion` 必须与原生二进制绑定。

| 变更类型 | 发布方式 |
|---|---|
| JS 逻辑、UI、文案、样式 | **EAS Update（OTA）** —— 秒级触达，可回滚 |
| 新增原生依赖、SDK 升级、权限声明变更、`app.json` 原生字段 | **必须重新 EAS Build**（OTA 推到旧二进制会崩） |

- `runtimeVersion` 采用 **`appVersion` 策略**（按原生版本号隔离）——保证 OTA 只会命中兼容的原生壳。
- **回滚**：EAS Update 支持把 channel 指回上一版本（`eas update:rollback`）；构建产物亦保留可重发。**发版前检查单**须验证回滚路径可用（见 §六）。
- **纪律**：**禁止**用 OTA 绕过发版评审——OTA 是**快速修复**通道，不是免评审通道；每次 OTA 同样在 `CHANGELOG.md` 登记一行。

---

## 五、版本号与 PC 发版对齐

移动端**独立版本号**（`versionName` / `CFBundleShortVersionString`），不跟随 PC 的 `0.9.x`。但**对应关系必须可查**：

| 登记项 | 位置 |
|---|---|
| 移动端版本 → 依赖的 server 契约版本（`openapi.json` 快照/commit） | `CHANGELOG.md` 移动端条目 |
| 移动端版本 → 对应 PC 发版 | 同上（一行「对应 PC vX.Y.Z 契约」） |
| OTA 更新记录 | `CHANGELOG.md`（含 channel 与 runtimeVersion） |

**要求**：移动端与 server 的契约兼容性**不得**靠「大概同步」——服务端破坏性契约变更时，须评估移动端存量版本影响并登记（移动端不像 Web 能强制刷新，**旧版本会长期存活**，这是移动端特有的兼容性负担）。

---

## 六、发版前检查单（内测）

1. `pnpm quality:gate` 全绿（含新增的 `test-mobile`）。
2. **L4 Maestro 主链**在 iOS + Android 真机各跑通一次（[测试策略](./测试策略.md) §一）。
3. **红线用例** D7（决策指纹拒批）/ D8（审计缺失不默认通过）通过。
4. 版本号已 bump，`CHANGELOG.md` 已登记（含契约对应关系）。
5. **回滚路径已验证**（EAS Update rollback 或保留上一构建产物）。
6. 若含原生变更 → 已走 EAS Build（**确认不是只推了 OTA**）。
7. 推送凭据（APNs / FCM）有效，且**登出解绑**逻辑已验（[后端适配清单](./后端适配清单.md) B1）。

## 七、安全与凭据（红线）

| 凭据 | 存放 | 纪律 |
|---|---|---|
| iOS 证书 / APNs Key | EAS 托管 + 公司密钥库 | **不入仓库**，不落开发机明文 |
| Android keystore | 公司密钥库（≥2 份异地）+ EAS | **丢失 = 无法更新存量用户** |
| FCM 服务账号 Key | 密钥库 + server 环境变量 | 不入仓库 |
| server 基址 / token | 构建期环境变量（EAS secrets） | 不写死进代码 |

**评审红线**：任何把上述凭据提交进 git 的 PR **一律拒绝**——这比功能缺陷更严重（凭据泄漏不可回收）。
