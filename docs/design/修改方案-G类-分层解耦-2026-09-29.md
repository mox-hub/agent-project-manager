# G 类修改方案：三层分层解耦——原语目录与语义组件层

> **本方案只做设计，不实施。** 它是 E 类方案 §七之十一（三）「新路线落地形态」四项中**任务 1（raw 出口重建）与任务 2（语义组件提炼）的承载设计**，并给任务 3（分层机械化）划出第一期；任务 4（requirement-intake 立项）由本文档本身完成。对应能力卡 **CAP-B-09**（B 治理线，状态 planned）。

## 〇、定位与一句话

**一行声明**：让裸原生元素「有归属」而不必全库改名——用目录物理隔离三层（原语 / 语义组件 / 存量原子），新组件只进新目录，依赖方向与出口规则按目录机械强制。

**用户裁决原话（2026-09-29）**：「我过去的经验已经证明了裸组件改造不是正确的方案，三个层级分层，对组件进行改造和解耦才是正解。」「重命名为 raw 的工作量级太大。系统内提供一个目录专门存放原语，新增的组件在新的目录里面，这样就不容易混淆了。」

**与原 §七之十（五）RawButton 方案的关系**：原方案（ui 内部 66 处 button + 2 处 input 换名 RawButton/RawInput）已被本方案**替代**——目录隔离达成同一目标（未来工具可识别非动作钮的归属），且零存量迁移。原裁决中仍然有效的部分：**RawButton/RawInput 的组件语义定义**（直通封装、不套基线、type 默认 button、非动作钮专用）原样搬入新目录，仅「位置」与「换名执行」两项改变。

**前轮教训三条（本方案的设计约束）**：

1. **同目录混放致混淆**——RawButton 与 Button 曾挤在同一 `ui/` 目录，是形变灾难轮「组件混乱」体感的一部分；本方案以目录为第一分隔。
2. **禁止全库 codemod 大轮**（§七之十一 裁决 5）——本方案的所有批次均为「新建 + 登记」，对存量业务面**零迁移**。
3. **治理链锚定目录**——registry / `gen-components-md` / 画廊 / `check-component-registry` 全部只认 `components/ui/`；新目录若不同步接入，就会成为第二个「无治理区」（比混淆更糟）。故 §四 的治理链改造与目录创建**同批落地**，不可拆。

## 二、设计：目录 = 层

### 2.1 三个目录与出口规则

| 目录 | 角色 | 形态约束 | 出口规则（谁能 import） |
|---|---|---|---|
| `components/ui/` | **存量原子组件**（Button/Card/Dialog/…） | 六轴/五轴既成事实，**轴冻结**（§七之十一 裁决 4：无组件立项不加轴）；新组件**不再进入本目录** | 业务面 / semantic 均可消费（现状不变） |
| `components/raw/`（新） | **原语层**：非动作交互元素的具名直通出口 | 直通封装：不套样式基线、无 cva 轴、`type` 默认 `button`、透传全部原生 props | **仅** `components/ui/` 内部与 `components/semantic/` 可消费；**业务面（modules/shared/app）禁入** |
| `components/semantic/`（新） | **语义组件层**：今后新增组件的默认落点 | 内部组合 raw + ui 原子；**props 面封闭**（不透传任意 `variant`/`className`，语义组件是基线变更的隔离层，§七之十一 裁决 3） | 业务面可消费（这正是它存在的意义） |

**命名**：`components/raw/raw-button.tsx` 导出 `RawButton`、`raw-input.tsx` 导出 `RawInput`（文件名与导出名沿用 §七之十（五）已裁决的命名先例，历史实现可直接从 backup 分支考取改造，grep 双锚点：目录 + 名字）。

### 2.2 依赖矩阵（lint:layers 扩展的 8 条规则）

| # | 规则 | 方向 | 违例语义 |
|---|---|---|---|
| R1 | modules/shared/app → `components/raw` | ✗ | 业务面必须经 semantic 或 ui，不得直取原语 |
| R2 | `components/raw` → ui / semantic / modules | ✗ | 原语在最底层，只准依赖 token/lib/原生（防环） |
| R3 | `components/ui` → semantic | ✗ | 原子不依赖上层（防环；ui→raw 见 R4 ✓） |
| R4 | `components/ui` → `components/raw` | ✓ | 原子内部的非动作钮改用具名出口（渐进，非批量） |
| R5 | `components/semantic` → raw / ui | ✓ | 语义组件的唯一实现方式 |
| R6 | `components/semantic` → modules | ✗ | 语义组件不得反向依赖业务 |
| R7 | `components/raw` 内部禁 cva / 基线样式类 | ✗ | 原语保持「裸」（代码审查约定 + 可选 lint 规则，见 G3） |
| R8 | `components/ui` 新增文件 | ✗ | 目录冻结：新原子件不再进 ui/（红利：ui/ 文件数只减不增） |

R1–R6 进 `lint:layers` 机械强制，**落地即 error**（裁决 G3：零存量违例的新目录规则不设 warn 期）；R7/R8 首期作代码审查约定 + registry 门禁侧校验（ui 目录文件清单快照，新增即报），二期机械化。

### 2.3 no-naked-controls 范围调整（与 R1 配套）

- `components/raw/` **整目录豁免**——原语的全部意义就是承载裸元素，扫它没有意义。
- `components/semantic/` **不豁免，且该目录内裸控件为 error 级**（裁决 G3）——语义组件内部必须用 RawButton 等**具名出口**承载交互元素，不得裸写 `<button>`；该目录全新零存量，一步 error 无清账成本，等于强制「有归属」落地到语义组件内部。
- modules/shared 口径不变（继续扫描、warn、长期盘点；裁决 G3：存量口径维持 warn 不动）。

- **按推荐通过**：G1 = a（`raw/` + `semantic/`）· G2 = a（仅 RawButton + RawInput）· G4 = a（存量不追溯）· G5 = a（Chip 示范）· G6 = a（registry `internal` 态、不出画廊）。

- **G8（裁决会新增裁决点）**：semantic 层 props 面封闭（不接 className、不透传 variant、不 extends HTMLAttributes）首期作审查约定、在批 G1 落实到 Chip 并成文；第二个语义组件出现时再抽 lint 规则转机械化。
